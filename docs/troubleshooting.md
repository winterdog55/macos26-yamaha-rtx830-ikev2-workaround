# トラブルシューティング

## プロファイルを入れても接続できない場合

まずどの段階で失敗しているかを切り分けます。macOS のログはコンソール.app で `NEIKEv2` を検索すると見られます。

| 症状 | 考えられる原因 | 対処 |
|---|---|---|
| プロファイルがインストールできない | XML が壊れている（リッチテキストで保存された等） | 標準テキストで保存し直す。`plutil -lint file.mobileconfig` で構文確認 |
| `NoProposalChosen` が返る | ルーターが AES-256-CBC / SHA2-256 / DH14 の組み合わせに未対応、または設定が異なる | ルーター側の設定を確認し、テンプレートの3値を合わせる |
| SA_INIT は通るが IKE_AUTH で失敗 | ID・PSK の不一致、またはプロファイルの PSK が反映されていない | `RemoteIdentifier` / `LocalIdentifier` を確認。加えて下記「PSK が反映されない場合」を参照 |
| 接続は成立するが通信できない | ルーティング、アドレス払い出し、フィルタの問題 | ルーター側のリモートアクセス設定を確認 |
| 接続後しばらくして切れる | 鍵の再生成（rekey）まわり | ルーター側の PFS 設定とプロファイルの `EnablePFS` を揃える |

## PSK が反映されない場合

プロファイルに `SharedSecret` を記入していても、インストール後に反映されず認証に失敗することがあります（実際に検証環境で発生しました）。

**対処（推奨）：** 下記の原因を修正したうえで、**古いプロファイルを削除してから入れ直す**のが確実です。システム設定 > 一般 > デバイス管理で該当プロファイルを削除し、修正したファイルを改めてインストールしてください。上書きインストールでは修正が反映されないことがあります。検証環境ではこの手順で PSK も含めて正常に接続できました。

**対処（応急）：** システム設定 > ネットワーク > VPN で該当の接続を開き、共有シークレット（事前共有鍵）を手動で入力しても接続できます。プロファイルによる暗号パラメータの固定は有効なままです。

**原因として最も多いもの（検証環境で実際に発生）：**

`<key>SharedSecret</key>` の行を、値だと勘違いして PSK で上書きしてしまうケースです。

```xml
<!-- 正しい -->
<key>SharedSecret</key>            ← 項目名。変更しない
<string>あなたのPSK</string>        ← ここに入れる

<!-- 間違い（この状態でも構文エラーにならず、インストールは成功してしまう） -->
<key>あなたのPSK</key>
<string>@@事前共有鍵@@</string>
```

この状態だと macOS からは「SharedSecret という項目が存在しない」と見えるため、認証情報のないプロファイルになります。同梱の `make-profile.sh` を使えばこの間違いは起きません。次のコマンドで確認できます（鍵そのものは表示されません）。

```bash
plutil -extract PayloadContent.0.IKEv2.SharedSecret raw あなたのファイル.mobileconfig > /dev/null \
  && echo "OK: SharedSecret は正しく設定されています" \
  || echo "NG: SharedSecret が見つかりません"
```

**その他に考えられる原因：**

- PSK に XML の特殊文字（`&` `<` `>` `"` `'`）が含まれている。XML ではそのまま書けないため、`&` は `&amp;`、`<` は `&lt;` のように書き換えるか、手動入力に切り替えてください
- テキストエディタが引用符を自動変換している（テキストエディットで「標準テキストにする」を実行していない場合など）

秘密情報をファイルに残さずに済むため、**最初から `SharedSecret` を空欄にして手動入力する運用**も有効です。

## 診断チャート（パケットを見る場合）

キャプチャ方法は [packet-flow.md](./packet-flow.md) を参照してください。

| 観測した応答 | 判定 | 対処 |
|---|---|---|
| `NO_PROPOSAL_CHOSEN` が返る | ルーターの提案が macOS 26 の廃止対象（DES / 3DES / SHA1 / DH14未満）に該当している可能性 | ルーター側を AES-256 / SHA2-256 / DH14 以上へ |
| `INVALID_KE_PAYLOAD` **だけ**の応答で Responder SPI がゼロ | 正常な動作（SA 未作成の段階） | 問題なし。次の応答を見る |
| 再送後の **SA・KE・Nonce を含む成功応答なのに** Responder SPI がゼロ | 本リポジトリが対象とするケースと同型。再送時のクライアント側 Initiator SPI が初回と同一かどうかも併せて確認すると切り分けやすい | このプロファイルで再送自体を発生させない＋ベンダーへ報告 |
| ルーター側ログにプロポーザルのパース失敗 | ルーターが新しい形式の提案を解釈できていない可能性 | ファーム更新を待つ／提案内容を最小化して試す |

## 固定するアルゴリズムの選び方

**Mac と VPN 装置の両方が対応している、安全な共通の組み合わせを1本だけ指定します。**目的は暗号強度を最大化することではなく、再交渉を発生させずに接続を成立させることです。強い方式を選んでも両側で噛み合わなければ接続できません。

目安:

1. AES-GCM や DH グループ19/20 が、**両側のリモートアクセス IKEv2 実装で利用可能なことが確認できている**なら候補になります（AES-GCM を使う場合 `IntegrityAlgorithm` は指定不要）
2. 対応状況が不明な場合は、まず実績のある **AES-256-CBC ＋ SHA2-256 ＋ DH グループ14**（本テンプレートの構成）を試してください

なお macOS 26 では DES / 3DES / SHA1-96 / SHA1-160 / DH グループ14未満が廃止されているため、それらは指定できません。ルーター側がこれらしか対応していない場合、このプロファイルでは解決できず、ルーターの更新が必要です。
